# 分支与发版模型（Branching & Release）

> 2026-11-10 生效。与《多模块发版管理方案与模板》（发布列车）配套。
> 节奏：**每周周五集成发版**；非周五只允许发 fix（hotfix）包。

## 线路角色

| 线路 | 命名 | 角色 |
|---|---|---|
| 主干 | `main` | 集成/发版线：交付包的**唯一来源**。只接受两类合入：① 周五集成 ② hotfix 回合 |
| 开发分支 | `feature/<主题>` | 一主题一支；窗口内开发；周五集成时合入 main；feature 之间不互合 |
| 修复分支 | `hotfix/<YYYYMMDD-主题>` | 非周五需发版时：从**最近一个 rel 标签**切出（不从 main），修复→打包→发版后回合 main |
| 基线修复 | `fix/<主题>`（历史遗留） | 从旧基线切的修复包（如 `fix/project-switch-v2.1fix`），确认退役前保留 |

## 每周节奏（发布列车）

- **周三（建议冻结日）**：停止本周 feature 合入；可开发版影响评审（30 分钟），产出《适配清单》。
- **周五（发版日）**：
  1. 评审后把本周 `feature/*` 合入 `main`（只合通过集成验证的；未就绪自动顺延，不硬塞）；
  2. 在 main 打注释标签 `rel/YYYYMMDD`（本期集成发版点）；
  3. 从**该标签提交**构建集成包，跑包门禁（`task_layer/tools/package_verify_*.py`）；
  4. 发版并登记《发布列车计划表》。
- 包一律只从标签提交构建；不从 main 中间态构建。

## fix 发版（非周五）

1. 从**最近的 `rel/*` 标签**切 `hotfix/<YYYYMMDD-主题>` —— 保证 fix 包 = 基线 + 修复，不夹带未发主线变更；
2. 修复 → 全量回归（P1 复现 / P2 A→B→A / P3 守卫）+ 包门禁 → 发版；
3. fix 包同样打标签：`rel/YYYYMMDD_<variant>`（例：`rel/20261110_v2.1fix`）；
4. 修复分支**必须回合 main**（保证下次集成含该修复）；
5. 记入《适配清单》并书面知会受影响模块（方案第六条例外热修条款）。

## 规则

1. 标签不可变、不可移动；打错了另打新标签。
2. 分支删除前必须确认已合入（`git merge-base --is-ancestor`）；历史 fix 分支保留并注明状态。
3. 发版前工作树须干净（`.gitignore` 外的未跟踪文件要么入仓要么清除）。
4. `git stash` 仅作备份，确认无用后才 drop。
5. 破坏性接口变更按方案第五节走弃用窗口，不入本周集成。
